# 篇幅分档规则

本文件定义 `unified-thesis-reviewer` 对不同篇幅论文的处理策略、进度反馈模板、耗时承诺声明。本文件是 `rules/orchestration-flow.md` §3A / §4 的展开。

## 索引

- 三档分档表：§1
- 分章合并规则：§2
- 进度反馈示例（至少 3 条）：§3
- 不承诺耗时声明：§4

---

## §1 三档分档表

| 档位 | 篇幅（字数） | 处理策略 | 触发方式 | 是否询问用户 |
|---|---|---|---|---|
| **小** | ≤ 30000 字 | 单次整体处理，一次性调用 TR 的九大维度 + 一次性调用 CC | 自动 | 否 |
| **中** | 30000 – 150000 字 | 分章串行处理：TR 逐章执行九大维度、CC 逐条校对；合并后统一报告 | 自动，无需用户确认 | 否 |
| **大** | > 150000 字 | 按 §3A 节点 C 询问：按章拆分（默认）或单次通读（警告上下文受限） | 节点 C 询问 | 是 |

### 1.1 阈值的理由

- **30000 字**：硕士学位论文单章或本科毕业论文的典型规模；大多数模型一次上下文可容纳
- **150000 字**：博士学位论文的上限典型值；超过此值即便分章合并也需提醒用户，避免 Agent "假装完成"

### 1.2 字数统计方式

- 按**去掉空白字符后的 Unicode 码点数**计数
- 不含参考文献、附录、致谢；但含脚注正文
- 纯文本输入按空格 / 换行拆词后累加

### 1.3 档位切换的边界处理

- 29999 字 vs 30001 字的差异**不影响**处理质量；阈值用于路径选择而非质量判断
- 若 Agent 在采集阶段无法精确计数（如超大 pdf 抽取不完整），**向上保守估算**——小档的实际字数 ≤ 30000，中档的实际字数 ≤ 150000；宁可多走一档分章也不要漏检

## §2 分章合并规则

中档（30000–150000 字）与大档选"按章拆分"时：

### 2.1 分章的切分依据

按以下优先级寻找章节切分点：

1. docx 中的 `<w:pStyle w:val="Heading1">` / `<w:pStyle w:val="Heading2">` 等样式
2. 段落文本匹配"第 X 章 / 第 X 节 / 第 X 部分"
3. 段落文本匹配"一、二、三、……"或"1. / 1.1"数字标题
4. 都找不到 → 按固定字数（如每 20000 字）硬切分，并在报告开头注明"章节结构未识别，按字数硬切分"

### 2.2 串行处理

- TR 的九大维度**逐章**执行：第 1 章走完九大维度 → 第 2 章 → ……
- CC 的引注校对**逐条**执行（CC 本身即按条目处理，不受分章影响）
- 每章的中间产物保留在内存中；不产生"逐章的半成品报告"交付给用户

### 2.3 合并策略

全部章节处理完毕后，合并器按维度聚合：

- 九大维度中每一维度的所有章节发现**合并**到对应章节下，保留定位（"§3.1 第 2 段"等）
- 致命问题（R1–R4）无论出自哪一章都合并到报告开头的"⛔ 致命问题"段落
- 修改优先级 Top 10 跨章综合打分，不按章截断
- 答辩质询问题按全篇综合，不按章罗列

### 2.4 分章的用户感知

- 分章**自动启用**时（中档）→ 用户看不到章节边界，仅通过进度反馈感知（§3）
- 分章**询问后启用**时（大档）→ 用户已知情；报告开头额外一行"已按 N 章分次处理后合并"

## §3 进度反馈示例

每完成一个九大维度的主维度或一个章节时，输出一条进度反馈。以下为至少 3 条标准示例：

### 示例 1：章节进度

> 已完成第 3 章第 2.1 节的论证深度分析，进入文献综述检查……

### 示例 2：维度进度

> 九大维度已完成 4/9，当前正在进行法规适用与时效性核实……

### 示例 3：引注进度

> 引注校对进度：已校对 47/58 条；3 条待联网核实，4 条信息缺失待用户补全……

### 3.1 进度反馈的写法要求

- 以**一句话**陈述当前状态 + 下一步
- 含**具体数字**（例如"4/9"、"47/58"、"第 3 章"），避免空话
- **不**预估剩余时间（见 §4）
- 两条进度反馈之间的间隔不设硬性下限，按实际完成节点输出

### 3.2 不该出现的反馈

- "稍等一下我在努力"（无具体信息）
- "很快就好"（涉及时间承诺）
- "第 3 章大概还需要 5 分钟"（涉及时间承诺）

## §4 不承诺耗时声明

本 skill **不**对任何篇幅段做出具体耗时承诺（不承诺 "X 分钟内完成"、"十分钟内出报告"、"1 小时出批注版"等时间指标）。

### 4.1 理由

- 宿主 LLM 的响应速度不在本 skill 的可控范围内
- 联网工具的吞吐（每次调用的往返时间）受网络状况 / 外部服务稳定性影响
- 用户在节点 A/B/C/D 的响应延迟不可预估
- 分章合并、issues.json 自校验、脚本回读等环节在不同硬件上耗时差异大

### 4.2 标准声明模板

在超大篇幅（> 150000 字）的报告开头、或首次用户询问"要多久"时，输出以下声明：

> 本 skill 不承诺具体耗时指标。宿主 LLM 的响应速度、联网工具的吞吐、用户的交互延迟均不在 skill 可控范围内。处理过程中会输出进度反馈，使你可以随时判断当前状态。

### 4.3 若用户坚持要估计

回答"**我不估计具体耗时**"，并引导用户关注进度反馈（§3）而不是耗时预测。不要迫于压力给出虚假时间承诺。

## §5 与 `rules/orchestration-flow.md` 的衔接

| 档位 | 触发步骤 | 是否触发节点 C |
|---|---|---|
| 小 | §4 直接整体执行 | 否 |
| 中 | §4 内部自动分章，主流程无感 | 否 |
| 大 | §3A 节点 C 询问后进入 §4 | 是 |

节点 C 的默认值为"按章拆分"；用户选"单次通读"时在 §4 的首条输出中警告"超大篇幅单次通读，结果可能受上下文窗口限制而不完整"（R11.3）。
