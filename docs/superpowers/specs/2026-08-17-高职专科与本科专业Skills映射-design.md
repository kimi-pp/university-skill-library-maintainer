# 高职专科与本科专业 Skills 相关性映射设计

日期：2026-08-17
状态：已完成会话方案确认，待用户审核书面规格

## 1. 背景

项目新增的 `高职高专Skills领域分类表.xlsx` 已覆盖高职专科的 19 个专业大类、97 个专业类及 Skills 领域归类，但没有教育部目录中的六位具体专业代码。现有项目已经完成 2026 年本科专业与研究生学科的相关性映射，本次在不改写既有研究生—本科交付物的前提下，建立一套独立、可审计的高职专科专业—本科专业映射。

本映射服务于 Skills 的学科标签、专业检索和跨层次内容召回。它不是教育部发布的专升本对应目录，不用于证明招生资格、报考条件、课程互认、学分转换、学历衔接或学位等同。

## 2. 目标与范围

### 2.1 目标

- 以教育部现行职业教育专业目录为准，完整收录所有有效的高等职业教育专科六位专业代码。
- 保留输入表中的 19 个专业大类、97 个专业类及 Skills 领域信息，并将其作为辅助分类上下文，而非相关性证据。
- 以现有已核验的 2026 年 883 个本科专业为本科端标准主数据。
- 建立高职专科具体专业到本科具体专业的可解释、分等级、多对多关系。
- 从具体专业映射自动派生 97 个专业类层级的聚合结果。
- 生成高职专科到本科、本科到高职专科的双向索引。
- 保留两端没有直接对应关系的目录项及明确状态，不只输出映射成功项。
- 输出可供 Skills 标签与检索消费的独立数据包和工作簿。

### 2.2 非目标

- 不建立或推断院校级专升本招生计划。
- 不判断某一高职专业能否报考某一本科专业。
- 不推断课程、学分、学历或培养方案等价关系。
- 不以输入表中的宽泛 Skills 领域相同为理由强行建立专业对应。
- 不修改现有研究生学科—本科专业映射工作簿及其数据包。

## 3. 目录来源、版本与事实保全

### 3.1 高职专科端

高职专科现行目录采用“基础目录加正式增补”的版本链：

1. 教育部《职业教育专业目录（2021年）》中的高等职业教育专科目录；
2. 教育部正式发布的 2025 年职业教育专业目录增补清单；
3. 教育部正式发布的 2026 年职业教育专业目录增补清单。

2026 年新增专业属于本次目录主数据，但须在版本说明中注明其自 2027 年起执行招生的时间边界。最终高职专科专业总数不预先写死，而由上述官方记录解析、合并、去重后计算，并由自动化测试断言。

主要官方入口：

- 2021 年目录通知：https://www.moe.gov.cn/srcsite/A07/moe_953/202103/t20210319_521135.html
- 2025 年目录增补相关通知：https://hudong.moe.gov.cn/srcsite/A07/moe_737/s3876_qt/202601/t20260105_1425685.html
- 2026 年增补发布：https://www.moe.gov.cn/jyb_xwfb/gzdt_gzdt/s5987/202607/t20260715_1443823.html
- 2026 年增补答问：https://hudong.moe.gov.cn/jyb_xwfb/s271/202607/t20260715_1443829.html

### 3.2 本科端

本科端复用现有映射项目中已经核验的教育部《普通高等学校本科专业目录（2026年）》883 个专业及其门类、专业类和目录属性，不重复建立另一份口径不同的本科目录。

### 3.3 来源台账

每个目录来源必须保存：来源标识、文件或通知名称、发布机构、发布日期、访问日期、原始网址、适用教育层次、基础目录或增补类型、本地快照路径、文件哈希、解析页码或表格位置、原始文本及采用说明。目录事实与项目派生判断分开存储，禁止用映射结论覆盖官方名称、代码或层级。

## 4. 数据架构与交付边界

本次建立独立的 `vocational_undergraduate_mapping` 数据域，复用既有本科主数据和映射规则枚举，但不向现有研究生—本科数据包写入高职字段。

核心数据对象包括：

- 高职专科官方目录主数据；
- 输入表的专业类—Skills 领域辅助分类；
- 本科 2026 目录主数据引用；
- 专业类候选种子规则；
- 具体高职专业覆盖规则；
- 全量候选映射；
- 逐高职专业人工复核台账；
- 正式映射主表；
- 高职专科反向索引；
- 本科专业反向索引；
- 97 个高职专业类聚合索引；
- 来源台账、字段字典和质量检查结果。

正式映射标识固定为 `VUG-<高职专科代码>-<本科专业代码>`。同一代码对只能存在一条正式关系。

## 5. 关系模型

### 5.1 映射粒度

正式判断的最小粒度是“六位高职专科专业—本科具体专业”。97 个专业类的结果必须由已接受的具体专业映射汇总，不允许把专业类规则直接包装成已经人工确认的具体专业关系。

### 5.2 关系等级与 Skills 行为

沿用既有研究生—本科映射的五级模型：

| 关系等级 | 判定原则 | Skills 行为 |
|---|---|---|
| 主映射/核心对应 | 培养对象、核心知识技能体系和主要职业方向直接连续 | 默认标签并参与精确检索 |
| 其他核心对应 | 同样具备直接连续性，但不是唯一首要对应 | 默认辅助标签 |
| 强相关 | 共享关键技术体系、主要实践方法或稳定职业场景 | 参与扩展检索，不作为主标签 |
| 延伸相关 | 仅在部分交叉应用、工具方法或特定场景中相关 | 仅在跨学科检索开启时召回 |
| 目录参考 | 为完整性或敏感边界保留，禁止后续标签消费 | 仅目录查看 |

### 5.3 主映射约束

- 每个高职专科专业最多一个本科主映射。
- 不为满足覆盖率强行设置主映射。
- 只有“主映射/核心对应”可以标记为主映射。
- “其他核心对应、强相关、延伸相关、目录参考”均不得标记为主映射。
- 没有合适本科对象时保留显式零映射状态及原因。

### 5.4 关系依据

每条被接受的关系至少包含一项正式依据：

- 主要培养或实践对象；
- 核心知识基础；
- 主要实践或研究方法；
- 关键技术体系；
- 典型职业或行业场景；
- 培养出口；
- 教育部目录或正式说明中的明确衔接；
- 跨学科应用关系。

专业名称相似、代码邻近、所属 Skills 领域相同只能用于发现候选，不能单独作为正式映射依据。

## 6. 候选生成与复核

### 6.1 候选生成

先为 97 个高职专业类建立保守的本科候选种子，再根据每个六位高职专业的培养对象和技术方向应用具体专业覆盖规则。候选生成综合使用：

- 高职专业大类、专业类和具体专业层级；
- 本科门类、专业类和具体专业层级；
- 名称词项及同义词；
- 培养对象、关键技术、实践方法和职业场景；
- 现有映射项目已经验证的跨学科边界规则。

宽口径专业类不得把全部候选无差别继承给每个具体专业；名称相同但培养对象不同的专业必须单独覆盖。

### 6.2 人工复核台账

每个高职专科专业必须且只能有一条复核台账记录。该记录必须完整划分其候选映射：

- `accepted_mapping_ids`：接受的候选；
- `rejected_mapping_ids`：拒绝的候选；
- `zero_mapping`：确认不存在直接或核心本科对应时的显式零状态；
- `review_status`、`review_note`、`reviewed_at`：复核状态、说明和日期。

所有候选必须恰好属于接受或拒绝集合之一，不得遗漏、重复或同时出现。正式映射仅从接受集合生成。

### 6.3 复核状态

允许的状态包括：

- 已依据规则复核；
- 高置信度候选；
- 存在歧义，建议学科专家复核；
- 已确认无直接对应；
- 尚未完成复核；
- 敏感专业限制；
- 目录版本差异待处理。

交付时不得存在“尚未完成复核”的高职专业。存在真实学科歧义时可以保留专家复核提示，但其每一条候选仍必须完成接受或拒绝判定。

## 7. 零映射与双向完整性

### 7.1 高职专科端

如果某一高职专业没有“主映射/核心对应”或“其他核心对应”，必须显式标记“无直接本科对应”；它仍可保留经复核的强相关或延伸相关关系。若完全没有任何可接受关系，则另外标记“无接受关系”。

### 7.2 本科端

全部 883 个本科专业均进入反向索引。没有任何高职专科对应的本科专业必须保留并标注“无高职专科对应”；只有强相关或延伸相关而无核心关系的本科专业须与完全零关系区分。

### 7.3 专业类聚合

97 个高职专业类全部进入聚合索引。聚合只统计其所属具体专业已接受的正式关系，并分别给出：

- 涵盖的高职专业数；
- 具有核心本科对应的高职专业数；
- 显式无直接对应的高职专业数；
- 各本科专业及其覆盖专业数；
- 各关系等级计数；
- 可被 Skills 消费与仅目录查看的关系数。

## 8. 敏感专业与军事对象边界

- 涉及武器、弹药、军用装备、兵器制造或明确军事作战对象的映射，只能保留为“目录参考”。
- 这类关系必须同时满足：非主映射、不可消费、不得产生默认标签、辅助标签、扩展检索或跨学科召回。
- 本科端兵器类及其他明确武器对象应进入限制清单，并通过数据模式和生成器双重约束。
- 公安、司法、应急、国防安全等公共治理或安全主题不因名称本身自动归入军事限制；应依据具体培养对象逐项判定。
- 质量检查必须扫描所有敏感关系，阻止可消费行为泄漏。

## 9. 工作簿结构

最终交付一份独立工作簿 `高职专科专业与本科专业Skills相关性映射.xlsx`，包含以下工作表：

1. `使用说明与版本`：用途、非用途、目录版本、执行时间边界和免责声明；
2. `高职专科专业目录`：现行全部六位高职专科专业；
3. `本科专业目录_2026`：复用并完整保留 883 个本科专业；
4. `高职本科相关性映射主表`：一行一条正式关系；
5. `高职专业反向索引`：覆盖全部高职专科专业及零映射状态；
6. `本科专业反向索引`：覆盖全部 883 个本科专业及反向零状态；
7. `专业类映射汇总`：覆盖输入表的 97 个高职专业类；
8. `规则与字段字典`：枚举、约束、映射等级、Skills 行为和零映射语义；
9. `来源台账`：官方来源与输入表来源记录；
10. `质量复核清单`：阻塞问题、专家复核项和提示项；
11. `统计总览`：公式化展示覆盖数、映射数、等级分布和质量状态。

高职和本科代码均按文本保存以保留前导零及本科代码中的 `T`、`K` 等后缀。统计公式必须可追溯到目录主表和映射主表，不允许手工填死。

## 10. JSON 数据包

除工作簿外生成机器可读 JSON 数据包，至少包含：

- `metadata`：生成时间、规则版本、目录版本、来源摘要；
- `vocational_catalog`：高职专科主数据；
- `undergraduate_catalog`：本科主数据引用；
- `mappings`：正式接受关系；
- `vocational_index`：高职专科反向索引与零状态；
- `undergraduate_index`：本科反向索引与零状态；
- `class_aggregation`：97 个高职专业类聚合；
- `sources`：来源台账；
- `qa`：阻塞、需复核和提示项。

工作簿和 JSON 必须由同一份已验证数据生成，禁止各自维护一套结论。

## 11. 质量门禁与验收标准

只有同时满足以下条件才可交付：

- 官方基础目录与 2025、2026 增补解析完成，现行高职专科代码集合与来源记录一致；
- 高职专业大类覆盖 19 个、专业类覆盖 97 个，输入表专业类与官方目录能够逐项对账；
- 本科目录精确覆盖既有 2026 年 883 个专业；
- 两端代码唯一且按文本保存；
- 每条映射两端代码均能在目录主数据中解析；
- 映射标识唯一，不存在重复代码对；
- 每个高职专业最多一个主映射，且主映射等级合法；
- 每个高职专业有且仅有一条完整复核台账，全部候选被接受或拒绝集合穷尽且互斥；
- 高职和本科两端所有目录项都进入反向索引，零映射与部分映射语义一致；
- 97 个专业类聚合完全由已接受的具体专业关系派生；
- 敏感或军事对象不存在可消费的 Skills 行为；
- `qa.blocking` 为零，专家复核项和提示项有明确对象与说明；
- JSON 数据包可重复生成且哈希稳定；
- 工作簿重新导入后数量、代码、公式和关键单元格值与源数据一致；
- 工作簿全部工作表完成渲染和视觉检查，无明显截断、公式错误、默认空白表或严重排版问题；
- 现有研究生—本科数据包和工作簿在本任务中保持不变。

## 12. 测试策略

实施采用测试驱动方式，至少覆盖：

- 官方目录解析的固定样例、跨页表格、增补合并和代码去重；
- 输入表 19 个专业大类、97 个专业类的精确覆盖；
- 数据模式枚举、必填字段和非法组合的正反向测试；
- 专业类候选种子与具体专业覆盖规则；
- 候选接受/拒绝穷尽互斥、复核台账全覆盖和显式零映射；
- 主映射唯一、等级与 Skills 行为一致性；
- 武器和军事对象不可消费的突变测试；
- 双向索引与 97 类聚合的可重算一致性；
- 数据包确定性生成；
- 工作簿导入校验、公式错误扫描、视觉渲染和代表性专业抽查。

## 13. 实施与版本控制

- 实施在独立 Git worktree 和独立功能分支中进行，避免污染当前包含大量用户改动的 `main` 工作区。
- 只提交本任务新增或修改的文件，不纳入用户已有的未提交文件。
- 目录采集、规则生成、逐专业复核、数据包构建和工作簿交付分阶段提交并设置可重复验证门禁。
- 全部测试通过、交付物复核完成后，再按用户批准的集成方式合并到 `main`。

## 14. 最终交付物

- 一份高职专科—本科专业 Skills 相关性映射 JSON 数据包；
- 一份 `高职专科专业与本科专业Skills相关性映射.xlsx` 工作簿；
- 全量高职专科复核台账、双向索引、97 类聚合、来源台账、质量复核和统计总览；
- 生成脚本、数据模式、规则文件和自动化测试；
- 一份实施报告，记录目录版本、覆盖数量、映射统计、零映射、限制关系、专家复核项和验证结果。
