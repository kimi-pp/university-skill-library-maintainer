# 財務自動化五層次框架

> 本 Skill 蒸餾自 McKinsey、APQC、Gartner、Deloitte、UiPath 官方研究，以及台灣財政部、勞工保險局直接查驗的法規。
> 核心使用場景：顧問診斷、ERP 選型、RPA 導入評估、CFO 說服、台灣財務數字化規劃。

---

## 框架概覽

財務自動化五層次是一個**嚴格有序的技術成熟度模型**，不是可以自由選擇進入點的功能清單。每一層依賴下一層的地基——跳層導入的失敗案例在金額上均以億元起算（Lidl €5 億、Hershey $1 億+、JP Morgan $62 億）。

```
Layer 5：智能化（Predictive）— 只有 7% 財務部門達到
  ↑ 依賴 Layer 4：即時數據管道
Layer 4：視覺化（Visualize）— T+0 幾乎不可能，T+7 是大多數企業實際水準
  ↑ 依賴 Layer 3：自動化數據流
Layer 3：自動化（Automate）— 只有 1% CFO 超過 75% 流程自動化
  ↑ 依賴 Layer 2：結構化數字數據
Layer 2：電子化（Digitize）— 電子發票、ERP 線上化
  ↑ 依賴 Layer 1：統一定義和規則
Layer 1：標準化（Standardize）— 科目表凍結、SOP書面化、職責分離
```

**現實分布（McKinsey CFO Pulse Survey 2024，126 位跨國 CFO）：**
- 41% 的 CFO：僅 25% 以下財務流程已自動化（卡在 L2/L3 邊界）
- 1% 的 CFO：超過 75% 已自動化
- 98% 已投資數位化，但落地率嚴重落後投資金額

## 回答工作流（Agentic Protocol）

**核心原則：財務自動化是工程問題，不是採購問題。遇到工具/廠商選型問題，先問「你現在在哪一層」，再問「你的目標系統有沒有 API」。**

### 實踐範例（使用者入門必讀）

**範例 A：模糊的「自動化」需求**
```
用戶：「我們想要自動化財務流程。」

正確流程：
1. 問：「你現在月結需要幾天？」
   用戶：「大約 12 天。」
2. 判斷：>10 天 = L1 未完成（七問體溫計）
3. 確認：「所有核心流程都有書面 SOP 嗎？」
   用戶：「沒有，AP/AR 都是依人經驗做。」
4. 建議：「先投資 L1 標準化（6-8 週），不要先上工具。
         跳過 L1 直接導入的案例，Lidl 花了 €5 億才明白這件事。」
```

**範例 B：工具選型問題**
```
用戶：「要用 UiPath 還是 Power Automate？」

正確流程：
1. 先問：「你主要要自動化哪個系統的流程？」
   用戶：「好會計和勞工保險局的月繳費。」
2. 查：好會計有 API 嗎？→ 無；勞保局有 API 嗎？→ 無（確認）
3. 回應：「兩個都沒 API，所以 UiPath vs Power Automate 不是重點。
   真正的問題是：月繳筆數多少？
   - 勞保（月 >100 筆）→ RPA 可考慮，但要加斷路器
   - 好會計（低頻記帳）→ 不值得 RPA，人工或 CSV 月度匯出」
```

**範例 C：ERP 導入諮詢**
```
用戶：「我要導入 SAP，怎樣確保成功？」

正確流程：七問診斷先行
Q1 月結幾天 → 15 天；Q2 有書面 SOP → 沒有；Q3 主資料重複 → 有
判斷：L1 未完成。導入 SAP 前必須先做標準化。

回應：「建議先 3-4 個月做 SOP 化 + 主資料清洗。
       原因：Hershey's 沒做這件事，ERP 上線後倉庫有貨卻顯示缺貨，
       搞丟 $1 億+ 訂單。SAP 是好工具，但地基要先打穩。」
```

### Step 1：問題分類

| 類型 | 特徵 | 行動 |
|------|------|------|
| **診斷問題** | 「我公司現在適合上哪個層次？」 | → 七問層次診斷 → 定位層次 → Step 3 |
| **工具選型** | 「要用 RPA 還是 API？」「ERP 哪個好？」 | → **先七問確認層次** → 再問目標系統 API 狀態 → 三叉路決策 |
| **ROI 估算** | 「導入後能省多少？」 | → 用 APQC 基準比對 → 三層 ROI 論述 |
| **台灣合規** | 「台灣電子發票怎麼做？」「政府系統能自動化嗎？」 | → 本地化約束 section + WebSearch 確認最新公告 |
| **失敗排查** | 「我的 RPA 一直出問題」「ERP 上完還是手工」 | → 先七問確認現在層次 → 對應模型 1（跳層必死）或模型 4（行銷 vs 真實數字）→ 找根因 |

**判斷原則：** 如果用戶在問工具（UiPath/Power BI/SAP），先確認他們在哪一層。工具問題 80% 是層次問題。

### Step 2：資料查詢（需要最新數據時執行）

⚠️ **必須用 WebSearch 獲取真實資訊，以下標注的數字可能因時間而變動。**

#### A. 看企業成熟度位置
- 月結天數（Close Days）：單實體目標 ≤3 天，多實體 ≤7 天
- 財務成本佔營收比（APQC 基準：頂尖四分位 <0.8%，一般企業 1.2-1.8%）
- 財務人員中 Excel 工作佔比（>60% = 尚在 L2）

#### B. 看台灣法規現況
- 電子發票 B2B 強制對象（需至財政部賦稅署確認最新公告）
- 勞保/健保/勞退申報：線上申報已可，政府系統介面穩定性查最新公告
- 商業會計法電子帳冊：「得」使用電子方式，非強制

#### C. 看工具 API 開放性（台灣常見系統）
- 鼎新 Workflow：API 相對封閉，需詢問官方 API Partner 清單
- SAP B1：有 Service Layer API（REST），文件相對完整
- Microsoft Dynamics 365：API 最開放，Dataverse + Power Platform 生態
- 勞工保險局/健保署/財政部系統：**無公開 API，只能 RPA 或手動**

#### 研究輸出格式
查詢完成後，先在內部整理事實，再進入 Step 3 輸出建議。
用戶看到的是基於確認事實的診斷，不是調研報告。

### Step 3：框架式回答

運用以下五個心智模型和決策啟發式，輸出具體建議。

## 五個核心心智模型

### 模型 1：「跳層必死」原則（Foundation-First）

**一句話：** 每一層都是下一層的地基。跳過標準化直接電子化，等於把不一致的數據高效存進系統；跳過電子化直接自動化，等於讓機器人快速複製人為錯誤。

**三個歷史案例（已驗證，A/B 級來源）：**

| 跳層路徑 | 案例 | 結果 |
|---------|------|------|
| 跳過 L1（標準化）→ L2（電子化） | Lidl SAP 實施（2011-2018） | 損失 **€5 億**，廢棄 SAP，回退原系統 |
| 跳過 L2（電子化）→ L3（自動化） | Hershey's ERP（1999） | 主資料不完整，**$1 億+** 訂單無法出貨，股價跌 10% |
| 跳過 L3（自動化）→ L4（視覺化） | JP Morgan London Whale（2012） | 手工 Excel 錯誤導致 **$62 億**損失，儀表板呈現的是錯誤數字 |

**失敗機制：**
- Lidl：業務邏輯（進貨價庫存）與 SAP 系統邏輯（零售價庫存）不匹配，拒絕做 L1 標準化，選擇大量定制，定制成本失控
- Hershey：ERP 上線時倉庫地點代碼未正確遷移（主資料 = L2 未完成），系統顯示缺貨但倉庫有貨
- JP Morgan：交易員維護「兩套帳」，對外儀表板基於手工 Excel 錯誤計算，視覺化呈現假象

**生成力測試（可以用來推斷新情境）：**
- 問：「我想直接上 AI 預測現金流，但 ERP 還沒統一」→ 答：L1 未完成，L5 無數據基礎，不可行
- 問：「我的 BI 看板數字每次都不準」→ 答：L3 未完成（數據管道有人工環節），L4 症狀

**局限：**
- 對「已強制導入某層」的企業（如 ERP 已上線但 L1 未完成），不能說「要退回去先做 L1」，而要說「在現有系統內補強標準化」
- 部分小公司（<10 人）可以壓縮 L1+L2 同步進行，但不能跳過

### 模型 2：就緒門檻量化（Readiness Gate）

**一句話：** 「感覺準備好了」不是升層條件。每一層有具體的數字門檻，低於門檻就升層 = 提前失敗。

**各層就緒門檻（業界共識指標）：**

**L1 → L2（標準化 → 電子化）：**
- 月結天數波動 ≤1 天（連續三個月）
- SOP 文件覆蓋率 ≥80%
- 科目表（CoA）凍結，過去 6 個月無未授權新增
- 主資料重複率 <5%（供應商/客戶）
- 職責分離（SoD）通過稽核

**L2 → L3（電子化 → 自動化）：**
- 月結天數 ≤10 天（單實體）
- 數據準確率：月結後手動調整金額 <0.5% of revenue
- 重複主資料 <5%（且有機制阻止新增重複）
- 核心流程（AP/AR/GL）至少 70% 電子化（非紙本）
- 有至少一個「快速勝利」流程候選（月 >200 筆、規則固定、無判斷例外）

**L3 → L4（自動化 → 視覺化）：**
- 月結天數 ≤7 天
- 核心流程（AP/R2R）自動化率 ≥50%
- 例外率（Exception Rate）< 10%（機器人處理不了需人工的比例）
- 系統間 API 連接穩定（無需每月手工修復）
- 有一個「可信的單一數據真相」（Single Source of Truth）

**L4 → L5（視覺化 → 智能化）：**
- 月結 ≤5 天（理想 ≤3 天）
- 歷史財務數據 ≥24 個月，且數據清洗完成
- 現有看板有固定使用者且被信任（CFO 做決策時引用看板數字）
- 有 FP&A 專職人員（非兼任）
- 組織接受「模型預測」的文化基礎

**局限：**
- 這些門檻是「充分必要條件的近似值」，不是完美標準；面對有其他強力補償的企業（如非常強的 IT 團隊）可適度放寬
- L4→L5 的文化門檻比技術門檻更難量化，需要與高管直接確認

### 模型 3：工具選型三叉路（Tech Tri-Path）

**一句話：** 工具好壞由「目標系統是否有 API」決定，不是由哪個工具更知名決定。RPA 是沒有 API 時的「不得不選項」，不是首選。

**決策樹：**

```
問：目標流程的系統有 API 嗎？
│
├── 是 → 再問：流程在同一個 ERP 系統內嗎？
│         ├── 是 → ERP 原生自動化（最穩、最便宜）
│         └── 否 → API 整合（跨系統）
│                   → 如果多系統 → iPaaS（Boomi/MuleSoft/Azure Integration Services）
│
└── 否 → 流程每月執行次數 > 200 筆且介面穩定嗎？
          ├── 是 → RPA（接受維護成本，建斷路器機制）
          └── 否 → 人工執行（不值得 RPA 維護成本）
```

**台灣本地情況（實際查驗）：**

| 系統 | API 狀態 | 建議路線 |
|------|---------|---------|
| 財政部電子發票平台 | 有（電子發票 API，有限制） | API 整合（需廠商資格申請） |
| 勞工保險局 | **無 REST API** | RPA 或手動 |
| 健保署 | **無公開 API** | RPA 或手動 |
| 鼎新 Workflow | API 相對封閉 | 以 ERP 原生功能為主，跨系統用 RPA |
| SAP Business One | Service Layer REST API | API 整合（有學習曲線） |
| Microsoft Dynamics 365 | Dataverse API，最開放 | API 整合 + Power Automate |
| 好會計/記帳士軟體 | 多數無 API，CSV 匯出 | RPA（低頻可手動） |

**RPA 的真正定位（澄清行銷話術）：**
- RPA 是橋接技術，填補「無 API 系統」的缺口
- 結構性弱點：介面改版就失效；維護成本被低估（50%+ 企業反映超出預期）；無法處理非預期例外
- 台灣政府申報系統（勞保/健保/財政部）：別無選擇，但要有斷路器機制（例外時自動通知人工）

**局限：**
- API 開放性是個動態狀態，需每 6-12 個月重新確認廠商的 API 政策
- iPaaS 工具（MuleSoft/Boomi）授權費用高，通常不適合台灣中小企業

### 模型 4：「行銷數字」vs「真實數字」識別法（Reality Gap）

**一句話：** 「90% 直通處理率」「T+0 即時看板」「AI 預測準確率 95%」這些數字都有嚴格的前提條件，在那個前提之下才成立。

**常見行銷主張 vs 真實條件：**

| 行銷主張 | 前提條件（通常不說） | 真實基準 |
|---------|-------------------|---------|
| AP 自動化 90% 直通率 | 已結構化的電子發票、供應商主資料完整、PO 格式標準 | 非結構化發票的 OCR 錯誤率仍 5-15% |
| T+0 即時財務看板 | 所有系統有 API 整合、無手工匯入、無人工審核環節 | 近 90% 企業需 >3 天產出完整財務報告 |
| AI 現金流預測準確率 95% | 乾淨的 24+ 個月歷史數據、穩定業務模式（非季節性劇烈波動） | 財務預測 MAPE 典型範圍：5-30%；標準月結後 5% 以上才算良好 |
| RPA 讓處理時間縮短 80% | 目標流程規則固定、無例外、每月 >500 筆、介面穩定 | 維護成本通常抵消 20-40% 的初始節省 |
| ERP 上線後財務自動化 80% | 實施前做了完整的 L1 標準化 + 主資料清洗 | Gartner：55-75% ERP 實施未達預期目標 |

**識別供應商過度承諾的五個問題：**
1. 「這個數字是基於什麼前提條件達成的？」
2. 「您能提供與我司規模相似、台灣本地的具名案例嗎？」
3. 「例外率（Exception Rate）是多少？剩下的由誰處理？」
4. 「維護成本包含在 ROI 計算裡嗎？」
5. 「達到這個效果的企業，他們的 L1/L2 完成度是什麼水準？」

**真實 ROI 基準（APQC，A 級）：**
- AP 自動化 ROI：30-300%（中位數 ~150%，1 年回收）
- 月結縮短從 8-10 天 → 4-6 天（自動化後），世界級 1-3 天
- 每 FTE 年處理發票量：手工 ~6,000 張 → 全自動化 ~23,000 張（3.8x 差距）

**局限：**
- 台灣本地企業的 ROI 數字沒有系統性研究，只能參考全球基準
- 這個模型有過度懷疑的風險：對確實成熟的系統環境，原廠數字可能是真實的

### 模型 5：台灣本地化現實約束（Local Friction）

**一句話：** 全球最佳實踐在台灣有三類摩擦：政府系統不開放 API、本地 ERP 生態相對封閉、B2B 電子發票尚未全面強制。

**台灣財務自動化的特殊現實：**

**1. 政府申報系統摩擦（半自動化上限）**
- 勞保申報（iLABOR）：無 REST API，介面相對穩定，月執行次數通常 >100 筆 → RPA 可行，但需設斷路器
- 健保費申報：無 API，可用 RPA（穩定性中等）
- 扣繳申報（稅務）：財政部有資料交換格式，但需進行申請
- 電子申報（E-Tax）：財政部電子申報軟體可批次匯入，需使用指定格式（非完整 API）

**2. 電子發票現況（法規確認 + 業界實踐）**
- B2C 電子發票：已成熟，消費者可用手機條碼儲存
- B2B 電子發票：**分階段強制，非全面強制**（2026-04-12 查驗）
  - 上市櫃公司及特定規模 → 已在強制範圍
  - 小規模（月銷售額 <NT$20 萬）→ 免開統一發票
  - 全面 B2B 強制時程：**尚未明確，建議向財政部賦稅署確認**
- 台灣 B2B 電子發票標準：MIG 3.2.1（現行）→ MIG 4.0（升版中）；Peppol 進度落後歐盟

**3. 台灣 ERP 生態選型（業界實踐）**

| 規模 | 推薦方向 | API 開放性 |
|------|---------|-----------|
| 1-10 人（記帳士代工為主） | 雲端記帳（好會計/帳友）+ 記帳士配合 | 低，以 CSV 匯出為主 |
| 10-50 人 | 好會計/iPayroll 搭配，部分用鼎新雲 | 中低 |
| 50-500 人 | 鼎新 DyCERP / SAP Business One / Dynamics 365 | 中（鼎新）到高（D365）|
| 500 人以上 | SAP S/4HANA / Oracle Cloud | 高 |

**4. 台灣政府系統 RPA 成本效益判斷**

台灣政府申報系統（勞保/健保/財政部）無 REST API，企業必須在「RPA」或「人工/外包」之間選擇。以下是判斷框架（非官方統計）：

| 公司規模 | 月申報筆數 | 建議方案 | 年度成本概估 |
|---------|-----------|---------|------------|
| 微型（<10 人） | <50 筆 | 外包給記帳士 | NT$5,000-10,000/月 |
| 小型（10-50 人） | 50-200 筆 | 人工申報 + 計畫性導入 RPA | 人工：約 0.5 FTE；RPA 建置：NT$15-30 萬 |
| 中型（50-200 人） | 200-1000 筆 | RPA 可行，需加斷路器 | 建置 NT$30-80 萬；維護 NT$10-30 萬/年 |
| 大型（200+ 人） | >1000 筆 | RPA 必要，需 IT 支援 | 含維護，投資回收期 18-24 月 |

**斷路器機制（必須設置）：**
- RPA 連續失敗 3 次 → 自動通知財務人員改為人工，記錄原因
- 每月第一次執行前：IT 確認政府網站是否更新版面
- 預期維護事件：勞保局介面每 12-18 個月改版一次，每次停機 2-3 天

**「不值得做 RPA」的判斷條件（任一成立）：**
- 月申報筆數 < 50 筆（維護成本抵消節省）
- 企業無 IT 人力支援（RPA 失效無人修復）
- 預計 12 個月內換系統（投資無法回收）

**5. 「假自動化」五種識別**

台灣企業常見的「看起來像自動化但其實不是」：
1. **Excel 巨集自動化**：巨集只能在同一個 Excel 裡跑，輸入還是手工
2. **CSV 匯出 + 匯入**：兩端都需要人按按鈕，中間只是省掉打字
3. **RPA 跑一半**：機器人抓資料，但還是需要人「看一眼確認才送出」（= 人是瓶頸）
4. **部門局部自動化**：財務部門內部自動化了，但業務部門還是用 Email 送單（端對端仍斷鏈）
5. **報表自動產出但數字手工更新**：Power BI 看板自動刷新，但數據來源是人工每週填的 Excel

**局限：**
- 台灣特定廠商的 API 開放性會隨版本更新變化，本文的資訊截止於 2026-04-12
- 中小企業特定行業（如製造業零件廠）可能有行業專屬 ERP，API 狀況需個別確認

## 決策啟發式（快速判斷規則）

### 1. 七問層次診斷法（最先問的問題）

在任何財務自動化諮詢中，先問以下七個問題，再決定建議方向：

```
Q1. 你們現在月結需要幾天？（<3天/3-7天/8-10天/>10天）
Q2. 所有財務流程都有書面 SOP 嗎？
Q3. 系統裡有沒有重複的供應商/客戶主資料？
Q4. 財務人員每天有多少時間花在 Excel 手工操作？
Q5. 數據從業務系統到財務系統，中間需要手工複製貼上嗎？
Q6. 你們現在的財務報告，CFO 需要等多久才拿到？
Q7. 你們之前嘗試過自動化或 ERP 導入嗎？碰到什麼問題？
```

**解讀邏輯：**
- Q1 >10 天 + Q2 無 → **L1 尚未完成**，先做標準化
- Q1 8-10 天 + Q5 需手工 → **L1 完成但 L2 未完成**，先電子化
- Q1 <8 天 + Q5 無需手工 + Q6 >5 天 → **L2 完成，進入 L3**，找自動化優先流程
- Q1 <5 天 + Q6 3-5 天 → **L3 進行中**，評估 BI 看板需求（L4）

### 2. 流程自動化優先度四象限

```
高頻次
    │
    │  B：高頻低規則      A：高頻高規則
    │  （半自動，人機協作） （全自動首選目標）
    │
    ├─────────────────────────────── 高規則化（可明確描述例外）
    │
    │  D：低頻低規則      C：低頻高規則
    │  （人工，不值得自動化） （考慮定期批次）
    │
低頻次
```

**A 象限（全自動首選）：** AP 發票接收與格式轉換、固定報表產製、薪資計算觸發、勞保費試算
**B 象限（半自動）：** AR 收款對帳（付款備注不穩定）、AP 三路比對（收貨單常延遲）
**C 象限（定期批次）：** 年度稅務申報彙整、固定資產折舊
**D 象限（不做）：** 首次供應商審核、爭議帳款解決

### 3. ROI 計算三層論述（配合不同對象）

| 層次 | 論述重點 | 適用對象 | 支撐數字 |
|------|---------|---------|---------|
| 第一層：直接成本 | 減少加班時數、減少外包費用 | 保守財務長 | AP FTE 產能 3.8x；月結縮 20-30% |
| 第二層：品質合規 | 減少錯誤率、降低稽核風險 | 風控導向高管 | 錯誤率：手工 1-5% → 自動化 <0.1% |
| 第三層：戰略洞察 | 財務從記帳轉向預測、支援更快決策 | CEO/Board | Hackett 世界級企業月結 4 天 vs 一般 8 天 |

### 6. L2→L3 首個自動化流程選擇框架

這是台灣企業最常問的問題：「我月結穩定了，ERP 也有了，下一步要自動化哪個流程？」

**進入 L3 的前提（先確認）：**
- 月結天數 ≤10 天 ✓
- 核心流程 ≥70% 電子化 ✓
- 有至少一個「快速勝利」候選流程（月 >100 筆、規則固定、無複雜例外）

**各功能面的優先判斷（台灣場景）：**

| 流程 | 適合 PoC 的條件 | 台灣特殊情況 | PoC 期程 |
|------|---------------|------------|---------|
| **AP 發票接收** | 月 >200 張，大多數來自電子發票 | 電子發票 API 已串接是前提 | 1-2 月 |
| **AP 三路比對** | PO 系統已統一，收貨單及時 | 常見陷阱：台灣製造業收貨單延遲 | 3-4 月 |
| **AR 收款對帳** | 銀行回單可下載、付款備注規律 | 匯款備注填寫不規律是台灣常見問題 | 2-3 月 |
| **勞保/健保申報** | 月 >100 筆員工，IT 有支援 | 政府系統無 API，需加斷路器 | 1-2 月（RPA） |
| **固定分錄過帳** | 有月度固定攤提（折舊/預付/預收） | ERP 多數有原生排程功能，不需 RPA | <1 月 |
| **薪資計算觸發** | 薪資系統已統一，規則固定 | 出勤例外（加班/遲到）仍需人工審核 | 2-3 月 |

**PoC 成功標準（必須同時達到 4/5 才可擴大規模）：**

| 指標 | 目標 |
|------|------|
| 例外率（Exception Rate） | <10%（90% 以上案件機器人自主處理） |
| 月節省人力時數 | >10 FTE-hours |
| 流程執行成功率 | ≥90%（不需人工介入） |
| 處理時間縮短 | ≥30% |
| 系統穩定運行 | 連續 3 個月無需修復 |

**最常跌倒的地方（台灣中小企業）：**
- 選了 AP 三路比對，但供應商 PO 格式不統一（還沒到 L2）
- 選了 AR 對帳，但客戶匯款備注混亂（需先標準化備注格式才能自動匹配）
- 選了勞保申報 RPA，但沒有 IT 支援維護（機器人失效無人修）

## 矛盾與內在張力

### 張力 1：台灣推廣「數位轉型」vs 政府系統無 API
台灣政府積極推動企業數位轉型，但政府本身的申報系統（勞保/健保/稅務）多數缺乏開放 API。這導致企業財務「最後一哩路」仍需 RPA 或人工。→ 啟示：台灣財務自動化的瓶頸不在企業內部，而在政府介面的開放程度。

### 張力 2：全球頂尖實踐 vs 台灣中小企業現實
APQC 的世界級基準（月結 4 天、每 FTE 23,333 張發票）是大型跨國企業達成的。台灣 90%+ 企業是中小企業，人員配置 1-3 人，「全自動化」往往不比「訓練好的兼職外包」更有 ROI。→ 啟示：為台灣中小企業設計的方案要以「減少錯誤 + 合規」為主要賣點，而非「省人力」。

### 張力 3：RPA 被過度銷售 vs RPA 的真實價值
顧問和廠商常把 RPA 當萬能解。但 RPA 的真實定位是「無 API 環境的過渡方案」，在台灣政府系統的特定場景有清晰價值，在有 API 的系統上使用 RPA 是浪費（比 API 整合更不穩定且更貴）。→ 啟示：建議 RPA 時必須先問「目標系統有 API 嗎」。

### 張力 4：「智能化」的行銷魅力 vs 只有 7% 企業到達
Layer 5（智能化、AI 預測）是最多廠商和顧問推銷的方向，但現實中只有 7% 的財務部門使用 AI/ML 解決方案。75% 財務預測仍靠 Excel。→ 啟示：賣 L5 方案給尚未完成 L3 的客戶，是在賣客戶不需要的東西。

## 誠實邊界

1. **台灣政府系統的 API 狀態是動態的**：本 Skill 的資訊截止於 2026-04-12。勞保局/健保署/財政部的線上系統功能每年更新，建議向各機關官網確認最新申報方式。

2. **B2B 電子發票強制時程未確認**：台灣 B2B 電子發票分批強制，全面強制時程尚無清晰公告。使用前請至財政部賦稅署官網確認最新通知。

3. **ROI 數字是全球基準，非台灣本地研究**：APQC/McKinsey 的基準主要來自北美/歐洲大型企業。台灣中小企業的實際 ROI 數字沒有系統性公開研究。

4. **台灣本地 ERP API 開放性**：本 Skill 的 ERP API 評估基於業界實踐了解，非廠商官方聲明。具體整合可行性需向廠商確認技術文件。

5. **「跳層必死」的例外**：對規模極小（5 人以下）的企業，L1+L2 可以同步進行而不必嚴格分期。失敗案例（Lidl/Hershey）均為中大型企業，小企業的成本風險量級不同。

6. **Layer 5 AI 預測**：財務預測 MAPE 5-30% 是業界典型範圍，但不同行業（如季節性強的零售）波動更大。AI 預測在數據不足或業務模式變化快的情況下，可能不比滾動人工預測更準確。

### 資訊不足時的追問順序

遇到情境不明確時，依序追問：

1. 先問「月結現在要幾天？」（決定成熟度位置）
   - 充分回答：「通常 10 天」或「8-12 天之間」
   - 不充分：「不太確定」→ 追問：「最近三個月的平均？或上個月結帳用了幾天？」

2. 再問「主要哪個 ERP 系統？版本？」（決定技術路線）
   - 充分回答：「鼎新 DyCERP」或「Excel + 記帳士」
   - 不充分：「我們用幾個系統」→ 追問：「財務數據主要存在哪個系統？」

3. 最後問「這個流程每月大約幾筆？誰在審核例外？」（決定自動化可行性）
   - 充分回答：「大約 300 張發票，財務主管最後審一遍」
   - 不充分：「看情況」→ 追問：「上個月大概處理了多少筆？」

**判斷邏輯：**
- Q1 + Q2 有明確答案 → 即使 Q3 不確定，也可提供初步診斷
- 三問都無確定答案 → 明確告知：「建議先做一週的流程盤點（現況訪談 + 樣本數據蒐集），再制定路徑，以避免導入前提不符。」

### 我應該明確說「不知道」的邊界情況

遇到以下問題，主動說「超過本 Skill 範圍」：

1. **具體廠商深度技術問題**（如：「SAP B1 的 Service Layer 能否整合 [第三方]？」）→ 說「需向 SAP 官方或認證廠商確認，本 Skill 只提供 API 開放性的一般評估」

2. **台灣以外的法規**（如：「新加坡電子發票怎麼做？」）→ 說「本 Skill 聚焦台灣本地化，其他市場請查驗當地稅務機關」

3. **行業特定流程**（如：「銀行衍生品確認流程怎麼自動化？」）→ 說「本 Skill 針對通用財務流程（AP/AR/月結），行業特定流程需要行業顧問」

4. **RPA 具體 Debug**（如：「我的 UiPath 在第 47 步失敗，請幫我找問題」）→ 說「具體技術 debug 超出範圍，請向廠商支援提報。本 Skill 可協助評估是否值得繼續用 RPA 或改 API 整合」

5. **組織設計決策**（如：「我們該不該建立共享服務中心？」）→ 說「組織設計超出本 Skill 範圍，但可協助評估建 SSC 後應從哪一層開始」
